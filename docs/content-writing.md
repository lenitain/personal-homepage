# 主页内容写作思路（Design Note）

> 这份文档仅作内部使用：是给我自己（以及后续的 coding agent）看的写作规范。
> **它不属于 `content/`** —— `content/` 是真正对外展示的网页内容，本文件只指导"怎么写这些内容"，绝不直接进页面。

## 目的

这个主页的每一页（项目、关于、博客等）最终要回答一个朴素的问题：**这套东西为什么值得存在 / 它的价值何在。**
写作的目标不是把每件事讲透，而是让读者在扫读之后就能明白价值所在。

## 核心原则

1. **从高处切入，先给"看到新意"的观点。**
   不要在读者还没理解前就堆一堆实现细节。先抛出一个让人"耳目一新"、反直觉的观察或说法，用它撬动兴趣。
   示例（dotfiles）："为什么不用镜像打包？——因为真实的运行环境其实信息量很少，几 MB 文本就够。"

2. **先回应读者必然的反问，再讲原理，最后得出结论。**
   读者读到你的做法时，通常会下意识提出反例（"为什么不直接 X？"）。文章要先接住这个反问，而不是抛出一个没有前因后果的结论。
   顺序是：**反问题 → 底层原理（为什么）→ 结论（所以这样做）**。

3. **讲清楚"为什么"，而不只是"做了什么"。**
   从高处、从动机出发，说明这么设计背后的道理。宁可少讲几个细节，也要把逻辑链条讲顺。

4. **聚焦价值，而不是过程。**
   突出"这么做最大的好处是什么"，让读者衡量过价值后愿意继续了解细节。即使不把每件事讲透，读者也知道这题目值不值得深入。

5. **条目化、每条短。**
   大段铺陈容易让读者走神。用短的 bullet，一条一个要点，方便扫读。

6. **对用户隐藏内部细碎实现。**
   只有自己才关心的内部切分（比如配置文件之间的边界、目录命名、技术琐事）不要呈现给用户。站在使用者的视角，只讲"大概做了什么"。

## 可参考的范本

`content/projects/dotfiles.md` 的 **Design & Bootstrap** 一节即为该思路的落地：
开头先抛"为什么不打镜像"的反问，再讲"环境信息量很少、本质是文本选择"的原理，最后落到"几 MB 文本即可复现完整环境、可 diff 可移植"，随后用短条目概括覆盖范围，以一条 `mise run bootstrap` 命令收尾。
